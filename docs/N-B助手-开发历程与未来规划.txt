N-B助手 · 开发历程、挫折、价值与未来规划

版本：2.2.82
整理日期：2026-11-21
项目定位：面向易助 ERP 的单据关系与数据自动化工具


============================================================
一、我们为什么做这个软件
============================================================

易助 ERP 里，很多业务数据不是“没有”，而是“藏在另一张单据里”。

一张采购发票的供应商，可能要回到采购单去找；
一张领料单的规格，可能要经过工单、工单单身、品号主档才能找到；
一张报工单的自定义字段，可能要按工单号去移转单单身匹配；
客户还会不断增加自己的自定义字段，字段关系只存在实施人员和售后人员的脑子里。

过去这些事情靠人做：

1. 打开目标单据；
2. 判断它和哪张单据有关；
3. 找到关联的单号、序号、类别；
4. 打开来源单据；
5. 找到对应字段；
6. 逐行复制；
7. 再检查有没有漏行、错行、重复。

单据少的时候还能做，单据一多就容易出错。更麻烦的是，很多关系是“隐性知识”：老师傅知道，新人不知道；这个客户知道，换一个客户又要重新问。

我们做 N-B助手，最初的想法很朴素：

把“人去找关系、人去复制值”的过程，变成“工具理解关系、工具批量执行、人负责确认”。

它不是要替代 ERP，也不是要绕过业务规则，而是把 ERP 里真实存在、但操作起来很费劲的数据关系，变成一个可预览、可备份、可重复使用的工具。


============================================================
二、开发历程
============================================================

（一）起步：从“能带值”开始

2026 年 9 月底，项目开始。最早的目标很具体：选择目标单据、目标字段、来源单据、来源字段，预览能带出多少行，确认后执行。

这个阶段解决了最基本的问题：

- 目标单据和目标字段可以选择；
- 来源单据和来源字段可以选择；
- 执行前可以干跑预览；
- 执行前自动备份数据库；
- 支持强制覆盖、建立触发器、合并显示等选项。

但很快发现，真正难的不是“写一条 UPDATE”，而是：

- 目标单据和来源单据到底靠哪个字段关联；
- 单头和单身是不是同一层；
- 一张单是不是有多个类别、多个工单、多个来源；
- 来源为空时算不算有效值；
- 触发器应该挂在哪张表上。

（二）深入：把 ERP 的单据关系一条条摸清楚

2.2.29 到 2.2.33 是一段密集的“补关系”阶段。

我们先后处理了：

- 触发器合并时重复声明变量的问题；
- 来源值为空字符串却被当成有效值的问题；
- 领料单/退料单同一单号不同类别混在一起的问题；
- 工单主件通过品号主档查品名、规格的问题；
- 单头字段对应多个来源行时的聚合问题。

其中最难的是“单头”和“单身”的区别。

同样叫“规格”，可能挂在单头，也可能挂在单身；同样叫“单号”，可能是目标单据的单号，也可能是来源工单的单号。选错一层，预览看起来有数据，ERP 画面却不显示。

2.2.31 增加了主档解析链路：工单主件品号 → 品号主档 → 品名/规格。
2.2.32 增加了类别条件：同一单号存在 82 领料、83 退料时，必须同时匹配“类别 + 单号”，不能只按单号关联。
2.2.33 把单头合并显示改成真正聚合：一行目标对应多条来源时，按目标主键分组、去重、拼接，而不是随机取一条。

这些工作看起来是“修BUG”，本质上是在把 ERP 的单据关系建模。

（三）挫折：触发器反复挂错，最后回滚

2.2.34 到 2.2.43 是项目最艰难的一段。

我们试图解决“单头字段要等单身插入后才能取到值”的问题，反复调整触发器的挂载位置、命名方式、合并方式、强制覆盖语义。结果出现了连锁问题：

- 有的单据漏填；
- 有的数量发生变化；
- 强制覆盖把整列清空；
- 触发器反复改挂载，旧触发器和新触发器互相干扰；
- 单头字段和单身字段写串。

最后在 2.2.44 做了一个痛苦但正确的决定：把核心代码回滚到 2.2.33 的稳定逻辑，撤销 2.2.34 到 2.2.43 的改动。

这次回滚的教训非常深：

1. 不能一次改太多层。触发器、关联、覆盖、显示要分开验证。
2. 不能只看预览有数据，要看 ERP 画面是否真的显示。
3. 不能用“再改一版”掩盖没有验证清楚的问题。
4. 用户说“先验证一张单据，没问题再做后续修改”，这句话必须当成开发纪律。

2.2.45 之后，我们重新从小处修：先修执行后单号显示，再修触发器冲突，再修强制覆盖，再修合并显示。每一步都尽量只动一个变量。

（四）稳定：触发器冲突、强制覆盖、合并显示

2.2.46 到 2.2.48 重点解决触发器冲突：

- 旧触发器可能挂在单身表，却写单头字段；
- 新触发器又挂到另一张表，导致同一字段被写两次；
- 只按触发器名字清理不够，必须按“目标表 + 目标字段”识别。

最终形成了两条原则：

- 单头字段只由单头触发器写；
- 单身字段只由单身触发器写；
- 同一目标表、同一目标字段，不允许两个 N-B助手触发器同时写。

2.2.47 把“强制覆盖”改成真正的覆盖：先清空目标列旧值，再填入匹配行，清空和更新在同一事务里，失败整体回滚，执行前仍然备份。

2.2.68 又把“合并显示”的语义定清楚：

- 不是“多取一条”，而是保留目标旧值，追加本次来源值；
- 重复值跳过；
- 强制覆盖和合并显示同时勾选时，合并优先，不能先清空；
- 这个规则对所有单据通用，不只采购发票。

这几条看起来简单，但它们是工具能不能被信任的基础。

（五）界面：从“能用”到“像一个软件”

2.2.49 到 2.2.61，主要做首次安装引导和工作台界面。

- 2.2.49：后端支持测试连接 dryRun、初始化状态；
- 2.2.50：首次安装引导：欢迎弹窗 → 数据库配置 → 欢迎页 → 工作台；
- 2.2.51：欢迎页改成全屏场景；
- 2.2.52：工作台外壳：顶部状态、左侧导航、跨表带值/触发器管理/系统设置；
- 2.2.53：目标在左、来源在右，先选目标再选来源；高级选项折叠，底部固定操作栏；
- 2.2.54 到 2.2.58：多轮主题调整，最后采用深空高对比风格；
- 2.2.59：修复“全新安装但已有旧配置时跳过引导”的问题；
- 2.2.60 到 2.2.61：全屏欢迎页、标题单行、进入工作台前预加载字典。

这段工作也遇到过问题：导航按钮被 CSS 隐藏、触发器页被嵌套在跨表带值页里、预览结果表格内部滚动导致页面卡住、主题改完后文字对比度不够。都是界面问题，但会直接影响用户对“这个软件靠不靠谱”的判断。

（六）深化：从“取得到”到“取得对”

2.2.62 到 2.2.72 是关系链最深的一段。

- 2.2.62 曾尝试让系统触发器也支持停用/删除，后来在 2.2.63 纠正：系统默认触发器必须只读，只有本工具创建的触发器才允许操作；
- 2.2.64 增加“清除目标字段”：先统计、二次确认、备份，再清空选中字段；
- 2.2.65 到 2.2.66 隐藏多余的映射信息条，修复预览结果区滚动；
- 2.2.67 到 2.2.68 修复合并显示的聚合和追加语义；
- 2.2.69 修复报工单单身取移转单单身自定义字段：按工单号直连，而不是经移转单头；
- 2.2.70 增加“移转单单身 → 工单 → 工艺路线 → 主要材料 → 规格”的复合链路；
- 2.2.71 增加工单取重工单、委外变更单的反向适配边；
- 2.2.72 允许“能关联、能流通”的反向直接取值，不再按业务流向自动排除下游单据。

到 2.2.72，注册表里已有 95 条经过审计的关系，覆盖采购、销售、生产、委外、财务等主要单据链。

（七）开发方式的变化

早期是“用户报一个场景，我们补一条链路”。
后来变成“先把关系注册表建起来，再做全量审计”。
再后来变成“每条链路要有可复现的测试数据、预览结果和回归用例”。

这是从“救火”走向“工程化”的过程。

我们开始明白：

- 一条链路能不能用，不能靠感觉，要靠数据；
- 一个功能能不能交付，不能只看代码，要看预览、执行、触发器、备份是否闭环；
- 一个软件能不能长大，不能只靠加功能，要靠关系模型、测试和可解释的规则。


============================================================
三、我们遇到的挫折
============================================================

（一）技术上的挫折

1. 单头/单身层级选错

最典型的例子是 JDA960 和 JDB960。

我们在单头字段 JDA960 里写入了值，数据库里确实有值，但 ERP 画面不显示。查了很久才发现，ERP 画面读的是单身 JDB960，不是单头 JDA960。

这不是工具“写库失败”，而是目标层级选错了。

类似的问题还有：

- 报工单的 960 应该取移转单单身，而不是移转单头；
- 移转单取工单主要材料规格，要经过工单、品号、工艺路线，不是一条直连；
- 领料单的规格要从工单主件走，不是从领料单自己的字段猜。

2. 类别混线

同一单号可能同时存在 82 领料、83 退料。
如果只按单号关联，就会把 82 的来源带到 83，或者把两个类别的值混在一起。

2.2.32 加了“类别 + 单号”的条件后，这类假“一对多”才消失。

3. 空值被当成有效值

早期来源字段是空字符串时，也会被当成有效值，导致预览行数虚高，执行后把空值写进去。

2.2.30 增加“非空过滤”后，预览才接近真实业务。

4. 触发器冲突

旧触发器可能挂在单身表，却写单头字段；新触发器又写同一字段。
表面看是“值不对”，实际是“两个触发器在打架”。

2.2.46 到 2.2.48 通过“目标表 + 目标字段”识别和清理，才把这个问题压住。

5. 合并显示的语义反复

一开始是“多行只取一条”，后来改成“聚合去重”，再后来才发现用户真正要的是“旧值 + 本次值追加”。

这不是纯技术问题，是需求没有说清楚。
2.2.68 把语义定死之后，才稳定下来。

6. 缓存和版本

链路注册表有版本号。代码改了但缓存还是旧版本时，界面仍然走旧链路，看起来像“改了没用”。

后来每次改链路都同步升版本，旧缓存自动失效。

（二）产品上的挫折

1. 功能越加越多，但用户仍然觉得“只是个传值工具”

我们一度把重点放在“支持更多单据、更多字段、更多选项”，但用户真正需要的不是功能数量，而是：

- 能不能少查一次；
- 能不能少错一次；
- 能不能把老师傅的关系留下来；
- 能不能在客户现场快速解决问题。

这让我们重新思考：工具的价值不是“能填多少字段”，而是“能不能把一件重复、易错、依赖经验的事情变得可重复”。

2. “独一档”不等于护城河

在易助这个细分里，把单据关系、自定义字段、预览备份、触发器做深，确实比通用表格工具更贴业务。

但“独一档”不代表别人抄不走。
真正的壁垒是：

- 对客户字段和单据关系的理解；
- 积累下来的关系模板；
- 现场交付和售后经验；
- 客户信任；
- 遇到问题能快速定位、敢负责。

代码只是载体，domain knowledge 才是核心。

真正的验证是：

- 有没有人愿意用它处理真实数据；
- 有没有人愿意为它调整流程；
- 有没有人愿意为它付时间、付预算、付责任。

（三）组织上的挫折

迷茫是正常的

开发这个软件是出于自己的想法，不是公司立项。
当个人热情遇到组织的不确定，迷茫是正常的。

但迷茫不等于停下来的理由，也不等于无限投入的理由。

正确的做法是：把“我要不要继续”拆成“用什么证据继续、到什么程度停止”。


============================================================
四、我们的工具到底有什么用
============================================================

（一）对实施和售后：把“查关系、抄字段”变成“选关系、做预览”

以前处理一张单据，可能要打开好几张表、问好几个人。
现在可以：

1. 选目标单据和目标字段；
2. 选来源单据和来源字段；
3. 工具自动判断关联链路；
4. 预览能带出多少行、带什么值；
5. 确认后执行，执行前自动备份；
6. 需要长期自动带值时，建立触发器；
7. 需要保留旧值时，使用合并显示。

它不能替代业务判断，但可以把业务判断之后最耗时的执行动作接过去。

（二）对客户：解决“标准功能不覆盖自定义字段”的问题

很多客户会有自己的 960、961 或其它自定义字段。
标准 ERP 不一定支持这些字段的自动带值，手工做又容易错。

工具的价值是：

- 不要求客户改 ERP 标准逻辑；
- 不要求每个客户都写一套存储过程；
- 把客户自己的字段关系配置成规则；
- 以后同类单据可以复用。

（三）对团队：把个人经验变成团队资产

老师傅知道“这张单要跟哪张单”，但新人不知道。
工具把这种关系显式化：

- 关系注册表；
- 字段映射；
- 预览结果；
- 触发器规则；
- 测试用例；
- 变更记录。

它让“我知道”变成“系统知道”，让经验可以传递。

（四）研发价值

1. 业务建模价值

不是简单写 SQL，而是把 ERP 的单据、单身、类别、主档、工艺路线、来源单号这些关系建模。

2. 工程安全价值

干跑预览、执行前备份、事务回滚、触发器冲突清理、系统触发器只读，这些设计让“批量改数据”这件事可控。

3. 交付效率价值

把逐单手工操作变成一次配置、批量预览、一次执行。
具体能省多少时间，需要在真实客户场景里记录，但方向是明确的：减少重复劳动和返工。

4. 可复用价值

95 条关系、若干复合链路、客户字段模板，可以复用到不同单据、不同客户。

5. 售后价值

很多售后问题不是“功能不会用”，而是“数据没带过来/带错层”。
工具可以快速定位是关系问题、字段问题、层级问题，还是数据本身为空。


============================================================
五、未来憧憬
============================================================

我们不想只做一个“传值工具”。

我们希望它最终成为一套面向 ERP 的数据自动化平台：

- 能理解单据关系；
- 能理解人的一句话；
- 能给出候选方案；
- 能先在预览里验证；
- 能在确认后安全执行；
- 能把这次配置沉淀成模板；
- 能在下一次遇到类似场景时直接复用。

最终目标：全面自动化，用自然语言语句解析来完成操作。

比如用户说：

“把采购单的供应商带到采购发票的供应商字段。”

工具应该能：

1. 识别目标单据：采购发票；
2. 识别目标字段：供应商；
3. 识别来源单据：采购单；
4. 识别来源字段：供应商；
5. 找到两者关系：采购发票 → 采购单；
6. 判断是一对一还是一对多；
7. 给出预览；
8. 询问需要确认的歧义；
9. 用户确认后执行；
10. 执行前备份，执行后给出结果和回滚点。

再比如：

“所有没带规格的领料单，按工单主件的规格补齐。”

工具应该能识别：

- 目标：领料单；
- 条件：规格为空；
- 来源：工单主件；
- 路径：领料单 → 工单 → 品号主档；
- 动作：只填空，不覆盖已有值；
- 风险：多工单时需要用户选择或合并。

这就是从“选单据、选字段”升级到“说一句话，工具帮你把关系、条件、动作、风险都拆出来”。

但全面自动化不等于“无人确认”。

ERP 数据不是测试数据，写错会影响生产、财务、库存。
所以未来的自动化必须有边界：

- 先预览，再执行；
- 高风险操作必须二次确认；
- 执行前备份；
- 支持回滚；
- 记录谁在什么时候改了什么；
- 系统触发器只读；
- 客户字段模板可审计；
- AI 只做识别、推荐、解释，不替人做最终决定。

我们理想中的产品形态是：

“关系大脑 + 自然语言入口 + 安全执行引擎 + 模板库 + 审计回滚”。

它既能让老手更快，也能让新手少犯错。


============================================================
六、用 5W1H 表述我们的项目
============================================================

一、Why：为什么做

因为 ERP 里大量数据关系是隐性的、重复的、依赖个人经验的。
人工跨单据查值、复制、补值，慢、易错、难交接。
客户自定义字段越多，这个问题越明显。
我们希望通过工具把“关系”变成可执行、可验证、可复用的规则，减少重复劳动和数据错误。

二、What：做什么

现在做的是：面向易助 ERP 的单据关系与跨表带值工具。
它能选择目标/来源、自动识别链路、预览、备份、执行、建触发器、合并旧值、反向取值。

未来要做的是：ERP 数据自动化平台。
用自然语言解析用户意图，自动生成关系方案，经过预览和确认后执行，并沉淀为客户模板。

三、Who：给谁用

直接用户：
- ERP 实施人员；
- 售后/运维人员；
- 熟悉业务、需要批量修数据的内部团队。

间接用户：
- 使用易助 ERP 的客户；
- 需要把字段关系标准化、交接给新人的团队。

参与者：
- 我：产品设计、开发、测试、现场验证；
- 业务/售后同事：提供真实场景、字段关系和验收；
- 老板/公司：决定是否给资源、客户试点、报销和推广支持。

四、Where：在哪里用

- 易助 ERP 的 SQL Server 数据库环境；
- 客户现场/公司内部测试环境；
- 售后处理数据的场景；
- 实施初始化、历史数据修正、字段补录场景。

五、When：什么时候做

- 现在：2.2.72 已可用，完成基础取值、触发器、备份、合并显示、反向取值；
- 近期：用一个小试点验证“省时、少错、可复用”，争取明确资源；
- 中期：做自然语言解析 MVP，先支持高频单据和字段；
- 长期：形成关系大脑、模板库、审计回滚和自动化执行能力。

六、How：怎么做

技术路径：
1. 维护单据关系注册表；
2. 用链路解析找到目标与来源的关联；
3. 生成可预览的 SELECT 和执行 SQL；
4. 执行前备份，必要时用事务；
5. 需要长期自动带值时生成触发器；
6. 合并显示保留旧值、追加新值；
7. 每次改动加回归用例。

产品路径：
1. 先做一个真实客户/真实场景；
2. 记录人工耗时、错误率、返工次数；
3. 用数据证明价值；
4. 把场景沉淀成模板；
5. 再扩到第二个客户/第二个场景。

============================================================
七、未来 12 个月路线图（建议）
============================================================

第一阶段：验证期（1 到 2 个月）

目标：证明工具在真实场景里“省时、少错、可复用”。

- 选一个客户、一个高频单据、一个自定义字段；
- 记录改造前人工耗时、错误次数；
- 用工具跑预览、执行、触发器；
- 记录改造后耗时和错误次数；
- 形成一页案例。

验收标准：
- 真实用户愿意继续使用；
- 数据可复现；
- 出问题能定位、能回滚；
- 有一组可展示的结果。

第二阶段：自然语言 MVP（2 到 4 个月）

目标：让用户用一句话描述需求，工具给出可确认的方案。

先做窄场景：
- “把 A 单的 X 字段带到 B 单的 Y 字段”；
- “把未填的 X 按 Y 补齐”；
- “这张单的 X 从上游 Z 取”。

能力：
- 意图识别；
- 单据/字段识别；
- 关系候选；
- 歧义追问；
- 预览；
- 确认后执行。

第三阶段：模板与关系大脑（4 到 8 个月）

- 客户字段模板；
- 常用单据链模板；
- 关系推荐；
- 数据体检；
- 批量修复；
- 执行审计和回滚。

第四阶段：全面自动化（长期）

- 多步骤任务；
- 事件驱动（新单自动带值）；
- 售后自愈；
- 权限与审批；
- 客户级配置；
- 可解释的 AI 建议。

原则：
- 先预览，再执行；
- 先单客户，再多客户；
- 先高频场景，再长尾场景；
- 先可解释规则，再智能推荐；
- 不拿生产数据做未经验证的实验。


============================================================
八、结语
============================================================

这个软件从“能带一个字段”开始，走到今天，已经不只是几行 SQL。

它包含了：

- 对 ERP 单据关系的理解；
- 对数据安全的敬畏；
- 对用户现场问题的响应；
- 对失败版本的复盘；
- 对“经验如何变成工具”的探索。

我们遇到过回滚，遇到过触发器冲突，遇到过“明明有值但 ERP 不显示”，也遇到过“做了很多功能，用户还是觉得只是个传值工具”。

这些挫折不是白经历的。
它们让我们知道：

- 不能一次改太多；
- 不能只看预览不看业务；
- 不能把口头支持当成资源；
- 不能因为年轻就低估自己，也不能因为做出一个工具就高估自己。

未来，我们希望它从“内部提效工具”成长为“ERP 数据自动化平台”：
让用户说一句话，就能把关系、条件、动作和风险拆清楚；
让每一次执行都可预览、可备份、可回滚；
让老师傅的经验留下来，让新人少走弯路。

这条路不一定快，但方向是清楚的：

把重复、易错、依赖个人经验的事情，变成可验证、可复用、可交接的自动化能力。

这就是我们继续开发它的理由。
